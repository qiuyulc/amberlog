# Amberlog 前端交互与视觉优化汇报

## 一、项目现状

Amberlog 当前前端是一个内嵌式单页控制台，提供三个主要页面：

- **检索**：条件检索、SQL 检索、时间分布图、字段筛选、详情查看、上下文浏览、查询历史。
- **台账**：展示数据集状态、数据量、存储层级、保留期和对账汇总。
- **对账**：按分钟展示采集端发送数、接收数、持久化确认数和对账判定。

当前页面使用 Preact 和原生 CSS 构建，JS、CSS 会被 esbuild 打包后内嵌到一个 `index.html`，再编译进 Rust 二进制。这样部署时只需要一个 Amberlog 二进制，不需要单独部署前端静态资源。

当前构建产物约为 **83.9 KB**，构建限制为 **200 KB（204,800 bytes）**，目前使用约 41%，暂时没有超过限制的风险。

## 二、当前已有能力

### 检索功能

- 条件模式和 SQL 模式切换。
- 字段名、运算符和字段值输入提示。
- 多条件组合和未生效条件提示。
- 时间范围快捷选择和自定义时间输入。
- 按时区显示时间，支持 UTC 和本地时间查看。
- 时间分布图，支持点击和拖拽缩放。
- 结果表分页、时间排序、字段隐藏。
- 字段栏分组、字段筛选和常见值展开。
- 单条记录详情、原始 JSON、上下记录浏览。
- 查询历史保存和恢复。
- 查询耗时、扫描文件、扫描字节数和扫描记录数展示。

### 台账和对账

- 台账展示数据集的总体状态和数据规模。
- 台账可以跳转到检索和对账。
- 对账支持按数据集和时间范围查询。
- 支持只查看非一致窗口。
- 展示一致、缺失、重复、待定和上报中断等判定。

### 通用能力

- 浅色、深色和跟随系统三种外观模式。
- 时区选择和时区持久化。
- 访问令牌只保存在当前浏览器标签页。
- 查询页面之间切换时保留当前状态。
- 页面不依赖外部 CDN 或第三方静态资源。

## 三、当前主要问题

### 1. 页面视觉层级较弱

当前样式以原生控件、简单边框和浅色背景为主，页面整体偏平，工具栏、结果区、字段栏和提示区域的层级不够明显。

深色主题主要是替换背景和文字颜色，缺少完整的深色视觉层级，因此部分面板、边框和次要文字的区分度不足。

### 2. 数据集名称在不同页面显示不一致

检索页面通常显示 `app`，台账和对账页面显示 `default/app`。这会让用户误以为是两个不同的数据集，也增加跨页面操作成本。

建议统一使用 `default/app`，或明确拆分显示组织和数据集名称。

### 3. 命中数量和扫描数量容易混淆

检索结果同时显示：

- 最终命中数量
- 当前页行数
- 实际扫描文件数
- 实际扫描字节数
- 实际扫描记录数

例如页面可能出现“共 148 条”和“扫描 202 条记录”。这两个数字统计口径不同，但当前页面没有解释，容易被理解为数据不一致。

建议将文案调整为：

```text
命中 148 条 · 第 1～100 行 · 实际读取 202 条 · 读取 4 个文件
```

并为“实际读取”增加悬浮说明。

### 4. 首次使用缺少引导

首次打开页面后，用户需要自行理解以下步骤：

1. 输入访问令牌。
2. 选择数据集。
3. 选择时间范围。
4. 添加条件并执行查询。

没有数据集、没有查询结果和令牌未填写时，页面的引导信息还不够明确。

### 5. 台账和对账信息密度过高

台账和对账表格字段较多，桌面端需要横向阅读，移动端体验会更差。当前所有信息都平铺在表格中，用户需要自己寻找重点。

建议将内容分为：

- 摘要信息：状态、条数、所在层、对账状态。
- 详细信息：时间范围、字节数、保留期和判定统计。
- 操作入口：检索、对账。

### 6. 详情侧栏的模态交互不完整

详情侧栏已经支持 Esc 关闭和上下记录切换，但还缺少：

- 背景遮罩。
- 打开时自动聚焦。
- 关闭后恢复原焦点。
- `aria-modal` 语义。
- Tab 键焦点限制。
- 移动端全屏或底部抽屉布局。

### 7. 部分交互依赖鼠标

时间分布图主要依靠点击和拖拽，结果表隐藏列按钮主要在鼠标悬浮时显示，字段详情和表格行的可操作性也不够明显。

建议补充键盘操作、明确的操作按钮和更明显的悬浮状态。

### 8. 错误和空状态缺少快捷操作

当前错误信息主要是文字提示，例如“无法连接服务”“查询写法有误”。建议增加重试、恢复上次查询和查看示例等操作。

### 9. 移动端布局支持不足

当前页面存在固定宽度输入框、固定宽度字段栏和多列数据表，没有专门的移动端布局规则。窄屏下容易出现拥挤和横向滚动。

### 10. 无完整的视觉和可访问性回归测试

现有测试重点覆盖查询请求、状态变化和页面交互，移动端布局、视觉回归、焦点管理和屏幕阅读器行为还没有形成自动化检查。

## 四、整体视觉优化方向

建议将前端改造成“日志检索控制台”风格，保留 Amberlog 的琥珀色品牌识别，同时引入更清晰的中性灰蓝色界面层级。

### 视觉基调

- 浅色主题：浅灰页面背景、白色内容面板、深灰文字、蓝色主操作。
- 深色主题：深蓝灰页面背景、分层面板、低亮度边框、浅灰文字。
- 琥珀色主要用于品牌、选中状态、时间分布图和提醒，不作为所有交互状态的通用颜色。
- 错误、成功、警告和待定状态使用统一的语义色和文字标签。

### 设计系统

统一以下设计变量：

- 页面背景、面板背景、浮层背景。
- 主文字、次要文字、禁用文字。
- 边框、分割线、焦点环。
- 主按钮、次按钮、危险操作按钮。
- 成功、警告、错误、待定状态。
- 4、8、12、16、24 像素间距体系。
- 统一圆角、阴影和控件高度。

### 页面结构

- 顶部导航改成稳定的应用头部。
- 查询条件、时间范围和查询按钮形成工具栏区域。
- 字段栏作为可收起的侧边面板。
- 结果区域使用统一的内容卡片。
- 详情使用带遮罩的侧边抽屉。
- 台账和对账增加顶部摘要区。
- 数据表支持固定表头和固定关键列。

## 五、建议的优化优先级

### 第一阶段：可用性和一致性

1. 统一 `app` 与 `default/app` 的展示方式。
2. 重命名并解释命中数、扫描数和当前页行数。
3. 增加首次使用、空结果、无令牌和错误重试提示。
4. 增加详情侧栏遮罩、焦点管理和移动端模式。
5. 增加结果行、分布图和隐藏列的键盘操作。
6. 统一按钮、输入框、标签、提示和错误状态样式。

### 第二阶段：整体视觉升级

1. 重构全局颜色、间距、圆角、阴影和字体层级。
2. 重新设计顶部导航和检索工具栏。
3. 优化检索结果表、字段栏和详情侧栏。
4. 将台账和对账改成“摘要 + 详细表格”的结构。
5. 增加桌面端、平板端和手机端布局规则。
6. 保持现有业务逻辑、接口和测试选择器不变，优先通过 CSS 和少量结构调整完成。

### 第三阶段：效率功能

1. 自动刷新和暂停刷新。
2. CSV、JSON 导出。
3. 复制查询和生成查询链接。
4. 保存常用查询和查询收藏。
5. SQL 示例、格式化和字段辅助。
6. 常用错误日志、最近数据和异常窗口快捷筛选。

## 六、前端体积控制方案

当前页面采用单文件内嵌方案，200 KB 是构建预算，不是浏览器的技术上限。

当前构建产物约为 83.9 KB，建议继续维持 200 KB 限制，并增加 160 KB 预警线。

在体积优化方面：

- 不引入 React、Ant Design、Element Plus 等大型 UI 框架。
- 不引入 Monaco、CodeMirror、Chart.js 等重量级组件。
- 图表继续使用 CSS 和原生 DOM。
- 日期和时区逻辑继续使用浏览器 `Intl`。
- 高级详情、历史和台账功能接近体积上限时再考虑代码分割。
- 如果改成多个 JS/CSS 文件，需要同步修改 Rust 静态资源路由、发布包和缓存策略。

## 七、验收标准

### 交互验收

- 检索、台账、对账三个页面之间的名称和跳转一致。
- 首次打开可以理解如何开始查询。
- 令牌错误、网络错误、查询错误都有明确处理方式。
- 详情侧栏支持鼠标、键盘和移动端操作。
- 分布图、表格行和列管理支持键盘操作。
- 查询状态、加载状态、空状态和错误状态清晰可见。

### 展示验收

- 浅色和深色主题均有清晰的背景、面板、边框和文字层级。
- 台账和对账在常见桌面宽度下不需要频繁横向寻找重点。
- 375px、768px 和桌面宽度下均可正常操作。
- 表头、关键列和详情内容在长数据下仍可定位。
- 错误、警告、待定和一致状态可快速区分。

### 工程验收

- 前端产物不超过 200 KB。
- `pnpm typecheck`、前端测试和构建检查通过。
- Rust UI 浏览器测试继续通过。
- 不增加不必要的运行时依赖。
- 不破坏现有 `/ui` 单页部署方式。

## 八、结论

Amberlog 当前前端功能基础已经具备，下一步重点应从“功能可用”转向“信息更清晰、操作更顺手、视觉更统一”。

建议先完成第一阶段的可用性和一致性改进，再进行整体视觉重构。视觉重构以现有 Preact 和 CSS 为基础，不引入大型组件库，在保持单文件部署和 200 KB 预算的前提下完成。
